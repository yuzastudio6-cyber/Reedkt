# Worker Tool Runtime Architecture

## Purpose

This document defines the future worker/tool runtime boundary for ReeditPro. It is documentation only. It does not install tools, execute workers, call providers, render media, connect Supabase, deploy Google Cloud resources, or add credentials.

## Core Rule

Workers execute approved plan snapshots, not raw chat. ReeditPro can be chat-native while still requiring every expensive or sensitive action to start from structured records:

- approved edit plan
- approved credit estimate
- reserved credits when generation, rendering, or export is required
- approved snapshot payload
- worker job payload with IDs and idempotency key
- storage object references instead of signed URLs
- provider/tool policy frozen in the approved snapshot

If a worker cannot complete the job inside the approved route, tier policy, fallback policy, credit estimate, or QA policy, it must stop and request a new approval path instead of improvising.

## Runtime Boundaries

Frontend code must not call OpenAI, Wan, Hailuo, Veo, Remotion workers, FFmpeg workers, Playwright/browser-capture workers, Google Cloud worker services, or provider gateways directly.

Backend/API and future Google Cloud workers may later:

- load trusted records from Supabase by ID
- read secrets from Secret Manager
- read/write private GCS objects
- update job status, events, assets, QA, revisions, exports, and audit records in Supabase
- enforce approval, credit, dependency, provider, render, and QA gates before expensive work

This repo currently remains mock-only for those paths.

## Service Role Boundary

`SUPABASE_SERVICE_ROLE_KEY` is server-only. It must never be imported into Vite/frontend code, placed in `VITE_*` variables, logged, added to database rows, or sent to worker payloads. Future service-role writes must happen through audited backend/worker code paths only.

Normal users should not directly mutate approved snapshots, credit ledger records, credit reservations, worker events, generated asset execution state, QA worker results, or final export status.

## Worker Payload Rules

Worker payloads must include:

- job ID
- workspace ID
- project ID
- approved snapshot ID
- edit plan ID
- worker type
- execution mode
- idempotency key
- attempt/max attempts
- source, segment, operation, visual asset, renderer layer, or tool strategy IDs when relevant

Generation, rendering, export, and generation-mode audio work require a credit reservation ID.

Worker payloads must not include:

- raw API keys
- provider secrets
- service-role keys
- signed URLs as source of truth
- raw prompt-only execution
- unapproved user chat as the only instruction source

## Storage References

Workers should use canonical GCS bucket purpose plus object path references:

`workspaces/{workspaceId}/projects/{projectId}/...`

Canonical storage records must not store signed URLs. Signed URLs are temporary delivery/access artifacts generated by a future signed URL service, not persistent source-of-truth records.

Source media, browser captures, generated assets, QA artifacts, previews, exports, and worker temp files are private by default unless a later reviewed policy says otherwise.

## Tool Execution Policy

Controlled tools and renderers are future worker capabilities, not frontend behavior:

- The production render stack is Hyperframe + Remotion + FFmpeg + libass + OpenTimelineIO.
- Remotion composes approved assets into the final canvas.
- FFmpeg/VapourSynth/Sharp/OpenCV style work is future worker preprocess/postprocess/QA work.
- Playwright/browser capture is future authorized worker capture only.
- AudioFlux and Signalsmith Stretch are future SoundSync/audio worker candidates.
- Revideo is evaluation-only/future-optional and is not a core runtime dependency unless a later approved review proves a concrete core-stack gap.

Browser/app capture must be user-authorized and must not bypass authentication, paywalls, CAPTCHAs, robots, rate limits, or site restrictions.

No tool package is installed or executed by this document.

## Idempotency And Locking

Every future worker job needs an idempotency key. Workers should claim jobs through a safe backend/service path, check dependency readiness, write append-style events, and avoid duplicate expensive work on retry.

Local failures should block only affected downstream work. Global failures should block final render/export until resolved.

## Logging

Workers must never log secrets, signed URLs, provider keys, service-role keys, private credentials, or raw sensitive data. Logs should use IDs, status, sanitized summaries, error categories, and non-sensitive metadata.
