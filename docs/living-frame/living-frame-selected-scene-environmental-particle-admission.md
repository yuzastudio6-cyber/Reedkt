# Living Frame Selected-Scene Environmental Particle Admission

Status: `source_contract_green_shared_interfaces_block_materialization`

Contract:
`living-frame-selected-scene-environmental-particle-admission-v1`

## Purpose

Living Frame must be able to keep a still asset largely static while selected
environmental details move: dust, smoke, mist, snow, rain, embers, water, or
another approved environmental treatment. This is selective motion, not an
instruction to generate a video or animate every pixel.

The current representative selected scene already identifies:

- one `environmental_effect` component;
- one `environmental_motion` activation;
- the `deterministic_particle_effects` capability;
- semantic `demonstrate` and `resolve` timing;
- procedural alpha;
- exact normalized geometry; and
- a `particle_emission_normalized` semantic motion track.

The new admission candidate binds those facts without inventing the effect
physics or claiming that the existing renderer can execute them.

## Exact source binding

The candidate revalidates:

- selected-scene binding;
- Living Frame component digest;
- current MasterTiming digest;
- Living Frame timing-binding digest;
- confirmed output-frame digest;
- component-geometry bundle;
- selective-motion reconciliation; and
- exact scene, component, activation, capability, and timing-phase lineage.

It derives width, height, FPS, active frame range, rect, pivot, anchor point,
and deterministic seed digest from server-held approved evidence. It accepts
no caller seed, dimensions, particle settings, prompt, paths, URLs, bytes,
credentials, commands, or environment.

## Motion-budget rule

Environmental particles are one ambient motion group. They must:

- remain subordinate to the primary visual action;
- have a bounded particle count;
- remain still outside the MasterTiming-bound active range;
- use procedural alpha;
- pass primitive and destination-composite QA; and
- never silently become generated video.

Exact particle physics, appearance, density, speed, turbulence, lifetime,
blend, and color remain a canonical style/motion owner decision.

## Typed profile gap

The current `LivingFrameComponentPlan` carries a summary and the general
`environmental_motion` mini skill, but it does not carry an immutable typed
environmental-effect profile.

The runtime must not decide that a component is dust, smoke, fog, rain, or
another effect by parsing:

- a component ID;
- the human-readable summary;
- a subject name;
- a genre; or
- a fixture example.

An approved typed profile reference is therefore required before
materialization. This is a real shared-interface gap, not permission to infer
physics from prose.

## PixiJS disposition

PixiJS already is the correct existing production-tool identity for
high-performance 2D particles. No new tool identity is required.

Current released private operation:

`tool.pixijs.render_pixi_scene.v1`

Bounded candidate operation:

`tool.pixijs.render_living_frame_environmental_particles.v1`

The candidate operation is not registered or dispatched by this slice.

The current operation is insufficient because it:

- is fixed to 640×360;
- is fixed to an opaque panel;
- renders one static PNG;
- has no typed particle profile;
- has no selected-scene lineage; and
- cannot supply time-sampled particle data to the current static-PNG Living
  Frame overlay input.

The correct future extension stays under the one PixiJS executable identity
and creates one cost attempt for one exact approved primitive work item.

## Remotion boundary

Remotion remains the final canvas. PixiJS may prepare a deterministic
time-sampled transparent primitive, but it may not own:

- final composition;
- captions;
- source audio;
- MasterTiming;
- global camera;
- public delivery; or
- final export.

The current private Remotion Living Frame overlay contract accepts one static
PNG per overlay. A released environmental primitive therefore also requires a
canonical time-sampled overlay adapter or an equivalent deterministic
primitive adapter. This slice does not mutate that shared renderer interface.

## Authority boundary

This candidate:

- is read-only;
- does not select an environmental profile;
- does not register an operation;
- does not create a work item or cost event;
- does not dispatch or execute PixiJS;
- does not persist an artifact;
- does not mutate the asset manifest;
- does not change Remotion;
- does not approve QA or private review; and
- does not authorize production or customer billing.

## Adjacent deterministic kernel candidate

`living-frame-environmental-particle-kernel-v1` now provides the bounded,
subject-neutral portion of the future continuation:

- seven typed restrained environmental-effect profiles;
- Visual Continuity Pack style, palette, lighting, depth, and motion-density
  binding;
- server-seed-derived deterministic one-shot particle state tracks;
- confirmed-frame and MasterTiming digest inputs; and
- explicit refusal of selected-scene, timing, operation, runtime, artifact,
  renderer, QA, cost, billing, or production authority.

It is deliberately not wired into this selected-scene admission. The approved
scene still lacks the immutable typed profile reference, and the current
canonical timing/motion contracts disagree on whether the five semantic
phases partition the full segment or the narrower visual range. Binding around
either missing owner would create a parallel decision or clock.

The adjacent
`living-frame-environmental-particle-operation-materialization-v1` candidate
also defines the closed future PixiJS request envelope and a process-bound
single-use private lease. It preserves the exact confirmed canvas, time range,
profile, state-sequence digest, fixed PixiJS entrypoint, transparent output,
and Remotion final-canvas ownership while keeping operation registration,
dispatch, runtime, artifacts, costs, QA, review, billing, and production
false. It consumes a verified kernel only; it does not bypass the missing
selected-scene profile or timing owners.

The adjacent
`living-frame-environmental-particle-sequence-observation-v1` candidate now
proves the process-private byte observation and measurement shape against a
controlled eight-frame 3840×2160 RGBA PNG fixture. It verifies exact frame
lineage, CRC/inflate/alpha behavior, settled endpoints, temporal variation,
and alpha-centroid movement while keeping PixiJS entrypoint/runtime,
artifact, canonical QA, review, cost, billing, and production evidence false.
It is not a substitute for the selected-scene, operation, or runtime owners.

See
`docs/living-frame/living-frame-environmental-particle-kernel.md` and
`docs/living-frame/living-frame-environmental-particle-operation-materialization.md`,
plus
`docs/living-frame/living-frame-environmental-particle-sequence-observation.md`.

## Required canonical continuation

1. Add an immutable typed environmental-effect profile reference to the
   approved selected-scene/component evidence; the adjacent catalog is a
   candidate, not the canonical selection owner.
2. Reconcile the canonical visual-range versus five-phase timing domain, then
   bind exact style and physics values to the existing motion-budget owner.
3. Extend the existing PixiJS identity with a closed, server-derived,
   time-sampled transparent particle operation.
4. Bind that operation to one canonical work item, asset-manifest output, and
   cost attempt.
5. Add the corresponding time-sampled Remotion overlay adapter while
   preserving Remotion as final canvas.
6. Run procedural-alpha, loop, motion-budget, destination-composite,
   narration/caption-safety, and private-review QA.
7. Keep operation registration, dispatch, release, and billing blocked until
   those shared owners release their evidence.
